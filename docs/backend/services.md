# Backend gRPC services

Reference for the gRPC surface of the Go backend, as it exists on branch
`sketch/04-08-26`.

Protos live under `api/proto/`; handlers under
`components/backend/internal/service/`. The generated stubs in
`components/backend/internal/proto/` are not documented here — they are
regenerated by `just codegen::proto` and must not be hand-edited.

## Where services are registered

Everything is wired in one place: `components/backend/internal/service/server.go`
(`NewServer`). `components/backend/cmd/service/main.go` opens the database, runs
migrations, seeds the admin user, and then calls `service.NewServer(...)`; it
registers nothing itself.

Eleven services are registered:

| Service | Proto package | Handler file |
|---|---|---|
| `HealthService` | `health` | `components/backend/internal/service/health_service.go` |
| `UserService` | `user` | `components/backend/internal/service/user_service.go` |
| `HackathonService` | `hackathon` | `components/backend/internal/service/hackathon_service.go` |
| `PageService` | `hackathon` | `components/backend/internal/service/page_service.go` |
| `PhaseService` | `hackathon` | `components/backend/internal/service/phase_service.go` |
| `TrackService` | `hackathon` | `components/backend/internal/service/track_service.go` |
| `ProjectService` | `hackathon` | `components/backend/internal/service/project_service.go` |
| `TeamService` | `hackathon` | `components/backend/internal/service/team_service.go` |
| `VoteService` | `vote` | `components/backend/internal/service/vote_service.go` |
| `ConfigService` | `hackathon` | `components/backend/internal/service/config_service.go` |
| `PrizeService` | `hackathon` | `components/backend/internal/service/prize_service.go` |

gRPC server reflection is enabled. The interceptor chain is
`AuthUnaryServerInterceptor` followed by the protovalidate interceptor, so
request-level constraints declared in the protos (`buf.validate`) are enforced
before any handler runs.

## Shared implementation pattern

**Constructor.** `NewXService(dbClient *ent.Client, enf *mw.Enforcer) *XService`
— stores the ent client and the casbin enforcer, and zero-initialises the
embedded `Unimplemented...` struct. The one exception is `NewHealthService()`,
which takes no arguments because it touches neither database nor authorization.

**Enforce first.** Handlers call
`s.enforcer.RequirePermission(ctx, hackathonID, object, permission)` before
touching data. `RequirePermission` maps a denial to `Unauthenticated` for the
anonymous subject and `PermissionDenied` for everyone else
(`components/backend/internal/middleware/rbac.go`). Where the hackathon ID is
not in the request — `PageService.Get`, `PhaseService.Get`,
`ProjectService.Get`, `TeamService.*`, most of `VoteService` — the handler must
load the entity first to discover its hackathon, then enforce; the load is a
bare existence lookup and leaks nothing beyond `NotFound`.

**Mappers.** Shared ent→proto mappers live in
`components/backend/internal/service/mappers.go`
(`userEntryFromEnt`, `hackathonEntryFromEnt`, `trackEntryFromEnt`,
`projectEntryFromEnt`, `pageEntryFromEnt`, `phaseEntryFromEnt`,
`submissionEntryFromEnt`, `teamEntryFromEnt`, `settingsEntryFromEnt`).
Capability mapping lives in `components/backend/internal/service/capability.go`;
vote mapping is local to `vote_service.go`; windows/forms mapping is local to
`config_service.go`.

**Shallow List vs deep Get.** `HackathonService` is where this actually differs:
`List` returns scalars plus computed status and capability states, while `Get`
embeds creator, modifier, tracks, projects, pages, phases, capabilities,
settings and the member roster. The other services reuse the same mapper for
both `List` and `Get`, so their responses are the same shape either way.

**Edit semantics.** `Edit*` requests use `optional` fields; the handler applies
only those the caller set (`if req.Title != nil { ... }`). Two handlers deviate:
`TeamService.Edit` tests `req.GetName() != ""` instead of the pointer (so a
description cannot be cleared), and `ProjectService.Edit` tests
`req.GetTrackId() != ""`.

**Timestamps.** Always `timestamppb.New(t)`; nillable columns are nil-checked
first and emitted as absent when unset (`optionalTimestamp` in `capability.go`).

**Errors.** `uuid.Parse` failures → `InvalidArgument`; `ent.IsNotFound` →
`NotFound`; `ent.IsConstraintError` → `AlreadyExists` or `FailedPrecondition`
depending on the site; anything else is logged with `slog.Error` and returned as
a generic `Internal` so driver detail does not reach the client.

## Authorization model in brief

Casbin objects are `hackathon`, `page`, `phase`, `track`, `project`, `team`,
`submission`, `user`; actions are `read`, `write`, `create`, `propose`. The
domain is a path: `/hackathon/<id>`, optionally extended to
`/hackathon/<id>/team/<id>` or `/hackathon/<id>/project/<id>` via
`mw.WithTeam(...)` / `mw.WithProject(...)`. The subject is the JWT `sub`
(Keycloak ID), or the literal `anonymous` when no bearer token is present. A
global `admin` (`g2`) bypasses the matcher entirely. Default policies are seeded
in `defaultPolicies` in `components/backend/internal/middleware/rbac.go`.

Two additional gates sit *alongside* casbin on the acting RPCs:

- **Capabilities** — `requireCapability` in
  `components/backend/internal/service/capability.go`. One `capabilities` row
  per hackathon per action; `enabled` is authoritative. `FailedPrecondition`
  when closed. **Anyone holding `hackathon`/`write` bypasses the gate entirely**
  so organizers can fix things outside the window.
- **Windows** — `requireWindowOpen` in
  `components/backend/internal/service/config_service.go`. Enforced only when a
  `hackathon_windows` row exists and the relevant instant is set;
  `FailedPrecondition` otherwise. Registration and submissions honour one-shot
  `*_override_until` extensions.

Gate coverage as implemented:

| Acting RPC | casbin | capability | window |
|---|---|---|---|
| `Hackathon.Join` | — (explicit anon reject only) | `register` | `registration` |
| `Project.Propose` | `project`/`propose` | `propose_projects` | `proposals` |
| `Project.SetPreference` | — (participant-row check) | `set_team_preferences` | `preferences` |
| `Team.CreateSubmission` | `submission`/`create` | `create_project_submissions` | `submissions` |
| `Team.EditSubmission` | `submission`/`write` | — | `submissions` |
| `Team.FinalizeSubmission` | `submission`/`write` | `create_project_submissions` | — |
| `Vote.SubmitVote` | — (jury/participant checks) | — (uses `settings.voting_enabled`) | — |

The `vote` and `view_results` capabilities exist in the vocabulary and are
reported to clients, but no handler enforces them.

## HackathonService

`api/proto/hackathon/hackathon_service.proto`

| RPC | Status | Auth |
|---|---|---|
| `List` | implemented | per-row, see below |
| `Get` | implemented | `hackathon`/`read` **and** confirmed membership |
| `Create` | implemented | `hackathon`/`create` on domain `/hackathon/*` |
| `Edit` | implemented | `hackathon`/`write` |
| `Delete` | implemented | `hackathon`/`write` |
| `EditCapability` | implemented | `hackathon`/`write` |
| `AdvancePhase` | implemented | `hackathon`/`write` |
| `EditSettings` | implemented | `hackathon`/`write` |
| `Join` | implemented | authenticated non-anonymous caller |
| `ApproveParticipant` | implemented | `hackathon`/`write` |
| `RemoveParticipant` | implemented | `hackathon`/`write` |
| `SubmitRegistrationForm` | implemented | JWT; `hackathon`/`write` only for `on_behalf_of` |
| `AddOwner` | proto-only | — |
| `RemoveOwner` | proto-only | — |

**`List`** runs no up-front enforce. Public hackathons are always returned;
private ones are filtered row by row with `Enforce(hackathon, read)`, so an
anonymous caller sees only public events. Filters: `visibility_filter`,
`owner_id` (matches the *creator* edge) and `participant_id` push down to SQL;
`status_filter` is applied after the query because `HackathonStatus` is computed,
not stored. Phases and capabilities are eager-loaded so a list can gate its own
buttons. When `participant_id` is supplied the response carries
`viewer_membership` for that user.

**`Get`** enforces `hackathon`/`read`, loads the full tree, then applies a second
check — `viewerMayOpenMemberView`: the caller must be a **non-waiting**
participant, a casbin `owner`, or a global admin. A waitlisted registrant holds
the `member` role and passes casbin but is still refused here with
`PermissionDenied`. Note that `AllowPublicHackathonAccess` (which would add the
wildcard read policy for a public hackathon) is never called by any handler, so
public hackathons are discoverable via `List` but not openable via `Get` without
membership.

**Status** is never stored. `computeHackathonStatus` in `mappers.go` derives it
at read time from `starts_at`/`ends_at`: no `starts_at` or `now < starts_at` →
`PENDING`; `ends_at` set and `now >= ends_at` → `FINISHED`; otherwise `ACTIVE`.
Both `Get` and `List` capture a single `now` for the whole response so the status
badge and the capability states cannot disagree about the time.

**`Create`** does five things and rolls back best-effort on each failure: creates
the hackathon; creates one `capabilities` row per capability, all `enabled=true`
(`defaultCapabilityEnabled` in `capability.go`); creates a `hackathon_settings`
row with both booleans `false`; grants the caller the casbin `owner` role;
inserts a `participants` row with `is_waiting=false` so the creator appears on
their own roster. Returns `{hackathon_id}` only.

**`Join`** rejects the anonymous subject explicitly, refuses a finished
hackathon, then checks the `register` capability and the `registration` window.
It is idempotent — an existing participant row returns success. A new joiner gets
`is_waiting=true` **and** the casbin `member` role: membership gates the
sensitive paths through `is_waiting`, while the role lets a waitlisted registrant
propose projects and see the private hackathon they signed up for.

**`ApproveParticipant`** flips `is_waiting` to `false` and (re-)grants the casbin
`member` role. **`RemoveParticipant`** deletes the row and removes the role.

**`EditSettings`** patches `registrations_enabled` / `voting_enabled` on the
settings row. Note the merge comment at `hackathon_service.go:330`: registration
is gated by the `register` **capability**, not by
`settings.registrations_enabled`, which remains editable but unenforced.
`voting_enabled`, by contrast, *is* the gate `VoteService.SubmitVote` reads.

**`EditCapability`** is an update, never an upsert — a hackathon with no row for
that capability gets `NotFound`. `open_in_phase_id`/`closed_in_phase_id` accept
an empty string to unlink and a UUID to link, and the phase must belong to the
same hackathon.

**`AdvancePhase`** declares the current phase and, in one transaction, flips the
`enabled` flag of every capability that has an opening phase to match
(`capability.Advance` compares phase *positions*, ordered by `starts_at` with the
ID as tiebreaker). Capabilities with no opening phase are left untouched, which
is what keeps manually-opened voting immune to advancing. Also writes
`hackathons.current_phase_id`.

**`SubmitRegistrationForm`** requires a `hackathon_forms` row with non-empty
`registration_fields`, else `FailedPrecondition`. Unknown response keys, missing
required fields, unknown consent keys and unticked required consents are all
`InvalidArgument`. `on_behalf_of` (organizers digitising paper forms) requires
`hackathon`/`write`. The unique `(hackathon, user)` index turns a second
submission into `AlreadyExists`.

**`Delete`** removes capabilities, settings, windows, forms, form responses,
prizes and participants, then the hackathon. Content-bearing hackathons
(projects, pages, teams) trip a FK constraint and get `FailedPrecondition` with
an "archive it instead" message.

## PageService

`api/proto/hackathon/page_service.proto`

| RPC | Status | Auth |
|---|---|---|
| `List` | implemented | `page`/`read`, with a public-hackathon fallback |
| `Get` | implemented | `page`/`read`; `page`/`write` if the page is hidden |
| `Create` | implemented | `page`/`write` |
| `Edit` | implemented | `page`/`write` |
| `Delete` | implemented | `page`/`write` |
| `MoveUp` | implemented | `page`/`write` |
| `MoveDown` | implemented | `page`/`write` |
| `SetOrder` | implemented | `page`/`write` |

`visible` and `order` drive the read path. `List` returns pages ordered by
`order`; callers without `page`/`write` see only `visible=true` rows. If the
casbin check fails, `List` re-checks whether the hackathon is `public` and
proceeds if so — winners announcements and wrap-up posts are public content.
`Get` mirrors this: an invisible page requires write access.

Ordering is dense and maintained server-side. `Create` assigns `max(order)+1`.
`Delete` removes the page and renumbers the remainder `0..n-1` in a transaction.
`MoveUp`/`MoveDown` take an optional `increment` (default 1), clamp to the ends,
and rewrite every page's order in a transaction. `SetOrder` requires the complete
set of page IDs for the hackathon — a partial list is `InvalidArgument`.

`Edit` covers `title`, `content` and `visible` only; the phase link is managed
from the phase side (`PhaseService.Create`/`Edit`).

## PhaseService

`api/proto/hackathon/phase_service.proto`

| RPC | Status | Auth |
|---|---|---|
| `List` | implemented | `phase`/`read` |
| `Get` | implemented | `phase`/`read` |
| `Create` | implemented | `phase`/`write` |
| `Edit` | implemented | `phase`/`write` |
| `Delete` | implemented | `phase`/`write` |

`List` orders by `starts_at` then `ends_at`. A phase owns at most one page: the
`page_id` field on `Create`/`Edit` links it (`""` unlinks, a UUID links after
verifying the page belongs to the same hackathon), and `Delete` unlinks the page
before removing the phase. Both `Create` and `Edit` run in a transaction so the
phase and its page link commit together.

`Create` ignores the request's `starts_at`/`ends_at` — a phase is created undated
and must be scheduled with a follow-up `Edit`.

## ProjectService

`api/proto/hackathon/project_service.proto`

| RPC | Status | Auth |
|---|---|---|
| `List` | implemented | `project`/`read` |
| `Get` | implemented | `project`/`read` |
| `Propose` | implemented | `project`/`propose` + capability + window |
| `Approve` | implemented | `project`/`write` |
| `Disapprove` | implemented | `project`/`write` |
| `SetPreference` | implemented | participant row + capability + window |
| `ExportPreferences` | implemented | `project`/`write` |
| `Edit` | implemented | project-scoped or hackathon-wide `project`/`write` |
| `Delete` | implemented | project-scoped or hackathon-wide `project`/`write` |

**`Propose`** creates the project with `status="proposed"`, optionally attached
to a track (which must belong to the same hackathon), and then grants the
proposer the casbin `owner` role on the project domain
`/hackathon/<id>/project/<projectID>`. Both `owner` and `member` hold
`project`/`propose`, so waitlisted registrants can propose.

**`Approve`** / **`Disapprove`** are one-line wrappers over `setApproval`, moving
`status` between `approved` and `proposed`. Neither updates the `modifier` edge.

**`SetPreference`** runs no casbin check. It requires the `set_team_preferences`
capability, that the caller has a `participants` row for the hackathon
(waitlisted counts — preferences are expressed before the roster cut), and the
`preferences` window. It adds the user to the project's `preferred_by_users`
edge; there is no unset counterpart.

**`Edit`** and **`Delete`** try the project-scoped domain first and fall back to
the hackathon-wide one, so both the proposer and the organiser pass. `Delete`
also removes the proposer's project-scoped `owner` role. `Edit` does not update
the `modifier` edge.

**`ExportPreferences`** returns every project in the hackathon with its
`preferred_by_users` list embedded (`ProjectWithPreferences`).

## TeamService

`api/proto/hackathon/team_service.proto`

| RPC | Status | Auth |
|---|---|---|
| `List` | implemented | `hackathon`/`read` |
| `Get` | implemented | `hackathon`/`read` |
| `Create` | implemented | `team`/`create` |
| `Edit` | implemented | team-scoped or hackathon-wide `team`/`write` |
| `Delete` | implemented | hackathon-wide `team`/`write` |
| `AssignUser` | implemented | hackathon-wide `team`/`write` |
| `RemoveUser` | implemented | hackathon-wide `team`/`write` |
| `CreateSubmission` | implemented | `submission`/`create` on the team domain |
| `GetSubmission` | implemented | `submission`/`read`, team-scoped or hackathon-wide |
| `ListSubmissions` | implemented | `submission`/`read`, team-scoped or hackathon-wide |
| `EditSubmission` | implemented | `submission`/`write` on the team domain |
| `FinalizeSubmission` | implemented | `submission`/`write` on the team domain |

Teams hang off projects, not hackathons: every handler resolves
team → project → hackathon before enforcing. `List`/`Get` check `hackathon`/`read`
rather than a team-specific object — there is no `team`/`read` policy in
`defaultPolicies`.

**Membership** is written twice: the `team_participants` join row and a casbin
`member` grant on `/hackathon/<id>/team/<teamID>`. `AssignUser` and `RemoveUser`
only *log* a casbin failure, so the two can drift. `Delete` detaches members
first to avoid the FK constraint.

**Submissions** are versioned per `(project, team)`. `CreateSubmission` computes
the next version as `count(existing) + 1` and writes `status=draft`; the unique
`(version, project, team)` index makes a concurrent second create fail rather
than silently duplicate. `GetSubmission` returns the highest-version submission
for the team; `ListSubmissions` returns all of them ascending.
`EditSubmission` refuses a submission whose status is already `final`
(`FailedPrecondition` — finalized submissions are frozen) and is window-gated so
post-deadline drafts cannot mutate. `FinalizeSubmission` sets `status=final` and
is capability-gated as well as permission-gated, so a draft made before the close
cannot be turned in afterwards.

`Edit` treats an empty string as "no change" rather than reading the `optional`
pointers, so a name or description cannot be cleared through it.

**`SubmitVote`** is the one with real policy in it:

- The anonymous subject is rejected outright.
- Only `single_choice` ballots are accepted. Ranked and points ballots return
  `InvalidArgument` (deliberately *not* `Unimplemented`, which capability probes
  read as "this RPC does not exist") because the `votes` table stores one row per
  `(category, voter)` and multi-row ballots need a schema decision first.
- Voting must be open: the handler reads `hackathon_settings.voting_enabled`, not
  the `vote` capability. Missing settings row or `false` → `FailedPrecondition`.
- For a `jury` category the voter must be in the category's `jury_members`.
- For an `all_participants` category, organizers are explicitly excluded —
  casbin `owner` on the hackathon or a global `admin` role gets
  `PermissionDenied` ("organizers do not vote") — and the voter must be a
  **confirmed** (`is_waiting=false`) participant.
- The unique `(category, voter)` index turns a double vote into `AlreadyExists`.

`ListVotes` and `ExportVotes` both go through `votesForExport`, which requires
`category_id` and enforces `hackathon`/`write` — raw ballots are organiser-only.
`ExportVotes`/`ExportResults` emit CSV or JSON bytes; any other `format` value is
`InvalidArgument`.

`EditVoteCategory` cannot clear a jury: proto3 cannot distinguish an empty
repeated field from an absent one, so a non-empty `jury_member_ids` replaces the
jury and an empty one leaves it alone.

The `Vote` proto entity declares `created_at`/`modified_at`, but the `Vote` ent
schema has no timestamp columns, so those fields are always zero.

## ConfigService

`api/proto/hackathon/config_service.proto` — all five RPCs require
`hackathon`/`write`.

| RPC | Status | Notes |
|---|---|---|
| `SetWindows` | implemented | Upserts the `hackathon_windows` row. Omitted timestamps are left unchanged (`SetNillable*` skips nil). |
| `OverrideWindow` | implemented | Requires an existing windows row (`FailedPrecondition` otherwise). `window` must be `"registration"` or `"submissions"`. `extend_minutes` is anchored at **now**, not at the configured close — "extend by 30 minutes" means 30 more minutes from this moment. Logs the reason. |
| `SetRegistrationForm` | implemented | Replaces `registration_fields` + `registration_consents` (JSON), creating the forms row if absent. |
| `SetSubmissionForm` | implemented | Replaces `submission_fields`. |
| `SetVotingPolicy` | implemented | Pins `mechanism`, `oneBallotPer`, `ownTeamVoting`, `organizerVoting`, `tieBreak` and an optional `scale` into `voting_policy` JSON. Returns an empty response. |

The windows written here are consumed by `requireWindowOpen`, which is called
from `Hackathon.Join`, `Project.Propose`, `Project.SetPreference`,
`Team.CreateSubmission` and `Team.EditSubmission`. The voting policy is stored
but not read back by any enforcement path.

## Regenerating

```bash
just codegen::proto      # Go + TypeScript gRPC stubs from api/proto/*.proto
just codegen::db-schema  # ent ORM code + components/backend/Schema.md
just api-change          # codegen::proto, then restart
just schema-change       # both codegens, wipe state, restart, reseed
```

`buf` is only on PATH inside the Nix dev shell (`just develop`).
