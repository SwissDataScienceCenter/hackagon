          Colour the timeline by
          
          
          
          
          
            The legend under the timeline is rebuilt from whichever of these is
            selected, and every count in it is tallied off the ticks that were
            actually drawn — so it always states the encoding you are looking at.
            The choice is remembered on this machine.
          
          
        
          

        
          
          
          Pass / fail — not in the recipe
          
          
          
            recipe.jsonl describes intent, not results. It has no status
            field: no line in it records whether an action passed, failed or was
            skipped on any run, so nothing here can colour by that on its own.
            What the recipe does state is the outcome each action
            asserts — “expected outcome”, above, colours by that, and
            the — actions that expect an error are asserting
            that error, not failing.
          
          
          
          
            No run report loaded — “run outcome” colours everything as unknown.
            
            
          
            
          
              To colour by what actually happened now, load a Playwright
              JSON report from your own journey run — it overrides the built-in
              snapshot. Nothing is uploaded and no network is used: the file is
              read in this tab.
            
          
            
          bash .claude/skills/hackathon-e2e/scripts/run.sh journey writes
              .artifacts/results.json on every run (the json reporter is in
              playwright.config.ts, so no > report.json redirection is
              needed — and none should be used: every command in this container
              prints Nix and quitsh noise to stdout first, which would not parse).
          
            
          
              
              
            
          
            
          
          
          
        
          

        
          
          
          The two fields the legend counts
          
          
          
            gate — the action names the RPCs it needs and
            self-skips until they exist. scripts/probe.sh
            probes the backend for them at run time, so a gated action starts
            running on its own the moment the RPC lands; nothing has to be
            edited. Drawn as a cap at the top of its tick.
          
          
          
          
            The whole vocabulary — every field an action can carry, in plain
            language, with a live example of each — is in
            ? What do these mean in the header.
          
          
          
          
            todo — a free-text note on the action:
            why it is written the way it is, or what to re-specify when a bug it
            pins gets fixed. Several are design justifications, so this is
            not a count of gaps and not a count of failures. Drawn as a
            cap at the bottom of its tick.
